## Design Specificity Verdict

**LLM assessment**：产品特有的信息架构，套在可互换的后台外壳里。状态机才是 DataSentry 的产品，但视觉上它只是重复 30 次的 20px 徽标；token 层（系统 CJK 字体、4px 间距、蓝/琥珀语义、6–10px 圆角、30px 控件）是任何内部管理台都能用的语法。真正属于这个产品的是：12 个状态压缩成 4 个色族、错误码嵌在状态徽标下、绑定/草稿版本列、与 JSONL 对齐的三位序号时间线、两步发布文案、检查点表、模型徽标。

**Deterministic scan**：文件级检测器 `detect --json index.html src/views/SessionsView.tsx` 返回 exit 0 / `[]`，但它明确提示：`.tsx` 只跑了正则规则，需要解析页面的规则（tiny-text、low-contrast 等）没有运行，`index.html` 也没覆盖——所以这是**低估，不是干净证明**。改用 CDP 对受控标签页扫描后，得到 1 条真阳性：`textarea.input.composer-textarea` 的 placeholder `#757575` 在深色面板上对比度 **3.74:1**，低于 4.5:1。没有发现误报。

**Visual overlays**：没有注入用户可见的 overlay。B 用独立 CDP 标签页跑检测器和截图，证据来自 CLI 输出、计算样式和截图，不是页面内高亮。

## Overall Impression

密度这次做对了：表格 13px、单元格 6px 纵向内边距、数字右对齐，单行 34.5px、双行 48.7px，一屏能扫 30 多个任务；事件时间线仍然是全产品最可信的一屏。最大的机会不在再加装饰，而在**把审批页从「哈希清单」改成「批的是什么」**——这是产品原则 2 的直接落点。

## What's Working

1. **密度落到了可读的边界**：单行行高 34.5px、表头 12px、正文 13px；audit 页 41 条记录仍能一眼扫完，数字列使用 tabular-nums。
2. **时间线是真正的设计决定**：等宽 seq/type、弱化摘要、状态圆点、序号与 JSONL 一致；93 条事件没有折行（类型列已从 170px 放宽到 220px）。
3. **token 与可访问性纪律**：语义色成对定义、深色不是反相、离线 CJK 栈、2px focus-visible、reduced-motion 生效；浏览器控制台无错误，1440/1024/760 无页面级横向溢出。

## Priority Issues

**[P1] 审批页显示哈希，而不是被审批的对象**
- **What**：`ApprovalsView` 和详情审批表以 `paramsHash`、`recipientsHash`、`toolName` 为主，收件人、文件名、格式、草稿版本都不可见。
- **Why it matters**：审批人无法回答「谁收到什么文件、哪个草稿」；产品原则 2 在唯一为它存在的页面上失效。
- **Fix**：把收件人、格式、文件名、草稿版本作为主信息；哈希移到「技术细节」折叠行。需要 API 暴露收件人/文件名，属于内容/数据层改动。
- **Suggested command**：`/impeccable shape approvals`

**[P1] 「确认投递」被埋在下半页，且和「发起发布」抢同一个视觉层级**
- **What**：最高后果的按钮在审批表里，发布面板仍保留主按钮「发起发布」；在 2471px 高的详情页上要滚动约 1400px 才能找到。
- **Why it matters**：审批通过后的下一步是投递，但界面把「再发起一次」和「确认投递」做成同等权重。
- **Fix**：`awaitingPublishConfirm` 时，把发布面板的「发起发布」替换成唯一的「确认投递 → 1 个收件人」，并就地展示绑定摘要。
- **Suggested command**：`/impeccable polish session-detail`

**[P1] 760px 下任务表被面板裁切，且无法横向滚动**
- **What**：760px 时创建时间列被切掉（`2026/10/29 15:49:1`），`.panel-body` 的 `scrollWidth == clientWidth`，设置 `scrollLeft` 无效；表格 right 758.7px，面板 right 744px。约 780px 开始出现，700px 时裁掉 74.7px。
- **Why it matters**：页面级 `scrollWidth` 仍是 0，所以这个问题不会触发常规溢出检查；「平板/手机只要不破版」的边界被打破。
- **Fix**：给 `.table` 一个略高于 min-content 的 `min-width`（约 740px），让 `.panel-body { overflow-x:auto }` 真正产生滚动；或在 ≤800px 允许时间/工作区列换行。改完在 760/390 复测。
- **Suggested command**：`/impeccable adapt`

**[P2] 表单可辨识度不足：placeholder 3.74:1，控件边框 1.70:1**
- **What**：深色 placeholder `#757575` 对 `#181b21` 为 3.74:1；`.input` 边框 `--border-strong` 对面板只有 1.70:1（浅色 1.65:1），而输入框填充色与面板相同，边框是唯一边界。
- **Why it matters**：composer 和人工复核输入框没有可见 label，placeholder 是唯一提示；控件边界低于 3:1 非文本对比度要求。
- **Fix**：`::placeholder { color: var(--text-muted); opacity: 1 }`；新增 `--control-border`（深色 `#626b78` ≈3.2:1，浅色 `#8a94a3` ≈3.1:1）用于 `.input` 默认边框，focus 仍用 accent。
- **Suggested command**：`/impeccable polish`

**[P2] 任务列表没有筛选、排序或分组**
- **What**：只有「刷新」；副标题说「17 个需要人工介入」，但 37 行无法按状态分开，11 条 `WORKSPACE_BOUNDARY_VIOLATION` 几乎一样。
- **Why it matters**：管理者打开页面先问「什么卡住了」，现在必须逐行读徽标。
- **Fix**：表格上方固定状态族 chips（需处理/等待审批/已阻断/已完成），默认「需处理」，表头支持按状态和创建时间排序。
- **Suggested command**：`/impeccable polish sessions`

## Persona Red Flags

**Alex（效率型用户）**：`role="link"` 的 `<tr>` 无法 Cmd-click、复制 URL 或新标签打开；没有方向键行导航；没有筛选/排序，11 条重复阻断只能肉眼扫；导航没有待审批数量徽标；只能手动刷新；哈希没有复制入口；93 条时间线没有「跳到第一个失败」。

**Sam（依赖辅助技术）**：发布收件人和人工复核依据输入框只有 placeholder、没有可见 label；`.ua-cell` 截断只靠 `title`（悬停）；表格没有 `<caption>`/`scope="col"`；13px 正文配 12px 弱化文字对低视力偏小；`role="link"` 放在 `tr` 上语义不匹配；复核按钮没有说明后果。好的部分：focus ring 和 reduced-motion 都真实生效。

**王敏（财务审批人，项目特定）**：在会议间隙一屏内完成审批。她没有待审批数量提示，必须主动点进「审批」才发现工作；审批卡给的是哈希，不是「8 月经营月报 → board@example.com、xlsx、82 KB」；有效期是绝对时间，没有剩余时长；已批准的发布上方仍留着可编辑的格式/渠道/收件人表单，她无法判断当前表单是否就是正在确认的那一版；发布面板和审批表之间隔着滚动。

## Minor Observations

- `login-dark.png` 实际是任务页的副本，审批页截图是空队列；证据文件会重拍。
- 「步」作为列名太隐晦；表头没有 sticky；`发起发布` 被 `report.status !== 'draft'` 禁用时没有可见原因。
- 检查点表重复 11 次「取数中」，`D:\…` 路径溢出。
- 空状态只有一句话（「队列是空的。」），没有下一步。
- 间距刻度跳过 7/9（24→32→40），可以接受但没写进文档。
- 客观通过项：控制台无错误；760/1024/1440 无页面级横向溢出（表格裁切是面板内的独立问题）；Tab 15 个停靠点全部有 2px 焦点环；Enter/Space 可打开任务行；reduced-motion 下过渡降到 0.01ms；两套 `theme-color` 正确。
- 密度实测：单行 34.5px、双行 48.7px；符合高密度目标，但双行行高比单行高 41%。
