## 2. PR2（进行中）：恢复与状态机

**目标**：消除恢复路径上的死局和"重启一次就换一种结局"的行为。  
**不做**：`MANUAL_REVIEW` 人工出口（R9，放 PR5）。

### R1 pi 循环的 `maxSteps` 必须在执行前生效

- [x] 修复
- [x] 单测/回归

**问题**：`maxSteps` 只在 `agent.prompt()`/`continue()` 返回后检查；真实模型持续调工具时循环无上限。  
**位置**：`packages/backend/src/agent/pi-loop.ts:257`（后置检查）、`beforeToolCall()` 入口。  
**修复方向**：在 `beforeToolCall` 里检查 `state.step >= maxSteps`：把当前 tool_call 记为 failed，写 `tool.call.failed`，设置 `state.fatal`（终态 FAILED），`agent.abort()` 并返回 `{block:true}`；后置检查保留为兜底，条件统一为 `>=`。  
**回归**：`maxSteps=1` 的 pi 会话跑两步计划，期望 FAILED 且只执行 1 步。

### R2 pi 的 PAUSED 恢复不能静默重跑；recovery 要按循环选择 runner

- [x] 修复
- [x] 单测/回归

**问题**：`PiAgentRunner.run()` 对 PAUSED 会删除 transcript、从 step 0 重跑；`runRecovery` 永远用 legacy runner。  
**位置**：`packages/backend/src/agent/pi-loop.ts:127-133`、`packages/backend/src/context.ts:657-674`。  
**修复方向**：
1. `PiAgentRunner.run()` 遇到 PAUSED 直接 `fail(ILLEGAL_STATE_TRANSITION, "pi 循环不支持就地恢复 PAUSED，请走 recover --execute 或人工处理")`，**绝不**删 transcript 重跑。
2. `runRecovery` 按会话状态选择：`agentLoop==='pi' && state===WAITING_APPROVAL` → pi runner；其余（含 PAUSED）→ legacy runner（legacy 有 `resumeFromCheckpoint`，从检查点继续，不重放已完成步骤）。
3. 在 README/注释里明确：pi 的 PAUSED 恢复由 legacy checkpoint 路径接管，这是本轮的取舍；真正的 pi checkpoint 恢复后续再做。
**回归**：pi 会话 PAUSED 时 `resumeSession` 抛 `ILLEGAL_STATE_TRANSITION`；`runRecovery({execute:true})` 不重跑已完成步骤。

### R3 `INIT` 不能被恢复流程转成 PAUSED

- [x] 修复
- [x] 单测/回归

**问题**：新建未执行的 Session 在 `INIT`，recovery 判为 `continue-from-checkpoint`，再执行 `INIT → PAUSED`，状态机非法。  
**位置**：`packages/backend/src/runtime/recovery.ts:85-89`、`:331-336`、`packages/core/src/state.ts:45-46`。  
**修复方向**：把 `INIT` 归入 `IDLE_STATES`（"尚未开始，等人工执行"），`scan` 返回 `skip-idle`，`recover` 不做任何转移。  
**回归**：新建未执行任务 `recover --execute` 不报错、状态仍为 INIT。

### R4 `apply-denial` 不能对 null approval 解引用

- [x] 修复
- [x] 单测/回归

**问题**：无悬挂调用时 `finding.approval` 来自 `pendingCall`，恒为 null；`normalize` 里 `finding.approval!.id` 空指针。审批被拒后进程崩溃 → 会话永久停在 WAITING_APPROVAL。  
**位置**：`packages/backend/src/runtime/recovery.ts:285-288`、`:417-419`。  
**修复方向**：inspect 里新增 `decideDenial(action, reason, approvalRecord)`，把 `latest` 审批写进 finding；两处 `apply-denial` 都走它。  
**回归**：构造"审批 DENIED + 调用已结束 + 会话 WAITING_APPROVAL"，恢复应转 BLOCKED/READY，而不是报错。

### R5 `already-published` 必须把会话收敛到 DONE

- [x] 修复
- [x] 单测/回归

**问题**：`finalizePublish` 先写 report 状态、再转 session；中间崩溃后 report=published、session=WAITING_APPROVAL。`reconcilePublish` 返回 `already-published`，recovery 直接 `return null`，会话永远卡住。  
**位置**：`packages/backend/src/runtime/recovery.ts:366-367`、`packages/backend/src/reports/publish-service.ts:521-555`。  
**修复方向**：`resolve-publish` 的 `already-published` 分支里，若会话是 `WAITING_APPROVAL` 或 `READY`，补一次 `→ DONE` 转换并写 `session.state.changed`；已是 DONE 则不动。  
**回归**：`simulate-interrupted-publish` 变体 + 直接构造 report=published/session=WAITING_APPROVAL，恢复后到 DONE。

### R6 新发布请求要结束被取代的旧调用

- [x] 修复
- [x] 单测/回归

**问题**：`revokePending` 只吊销旧审批，不结束旧 tool_call；反复发起发布会留下多条 pending，recovery 取 `pending[0]`（最旧的）误判，`resume` 因 `pending.length !== 1` 失败。  
**位置**：`packages/backend/src/reports/publish-service.ts:204-205`、`:256`；`packages/backend/src/runtime/recovery.ts:201`。  
**修复方向**：
1. `requestPublish` 在 `revokePending` 前，把同一 Session 上旧的、仍为 `pending` 的 publish tool_call 标记为 `denied`（`APPROVAL_INVALID`，reason="被新的发布请求取代"）并写 `tool.call.failed`。
2. recovery 取悬挂调用时用**最新一条**（`pending[pending.length - 1]`），兼容历史脏数据。
**回归**：连续两次 requestPublish，pending 仍为 1；恢复/恢复执行不误判。

### R7 `confirmPublish` 必须幂等

- [x] 修复
- [x] 单测/回归

**问题**：只检查审批 `GRANTED`，不检查报表是否已发布；重复确认会重放网关调用并重复写 `publish.executed`/`receipt.received`。  
**位置**：`packages/backend/src/reports/publish-service.ts:305-410`。  
**修复方向**：加载 report 后，若 `report.status === 'published'`，返回 `{status:'already-published', receiptId, report}`（扩展 `ConfirmPublishResult`），不执行、不写事件；路由与 Web 增加该状态处理。  
**回归**：连续两次 confirm，第二次返回 already-published，事件数不增加。

### R8 网关只在"明确未发出"时删除 intent

- [x] 修复
- [x] 单测/回归

**问题**：`catch` 对所有异常都 `rmSync(intentPath)`，包括 SMTP/HTTP 超时、连接中断这类"可能已发出"的错误；重试可能真的发两次。  
**位置**：`packages/backend/src/sources/local-handlers/publish-gateway.ts:388-396`。  
**修复方向**：新增 `isDefinitelyNotDelivered(err, channel)`：
- email：仅 `ECONNREFUSED` / `ENOTFOUND` / `EAI_AGAIN` / `EAUTH` / `EENVELOPE` 视为明确未发出；
- im：仅 `WecomError`（平台返回 errcode）视为明确未发出；
- 其余（超时、socket 中断、未知错误）保留 intent，下一次以 `RECEIPT_UNKNOWN` 拦下。
需要导出 `WecomError` 或按 `name` 判断。  
**回归**：模拟 SMTP 超时 → intent 保留，第二次调用 `RECEIPT_UNKNOWN`；模拟连接拒绝 → intent 删除，可重试。
