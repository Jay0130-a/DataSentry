# DataSentry 工程问题复盘

这份文档记录 DataSentry 从 M1 到 M4、以及之后把 Agent 循环迁移到 pi 的过程中**真实遇到**的问题：现象、根因、当时的取舍、最后的修法。

写它的目的不是罗列「用了什么技术」，而是留下一批可复述的**判断过程**——面试里被追问「遇到过什么坑」时，能讲清楚「我怎么发现的、当时怎么权衡、为什么最后这么改」的人，和只能说出「我用了微服务」的人，是两种评价。

阅读建议：第一节的九个问题值得完整讲；第二节是速查表，用来应付「还有别的吗」；第三节是贯穿全程的原则，被追问「你的工程判断是什么」时用。

---

## 一、九个值得展开讲的问题

### 1. 审批绑定可以被绕过：摘要字段与参数不是同一份数据

**现象**

M4 写「审批漂移」回归样本时，我设计了一种攻击：悬挂的工具调用已经批过，**只改参数、不改参数摘要字段**。写测试时我意识到，当时的实现很可能挡不住。

回头看代码，确实挡不住：

```ts
const paramsHash = record.paramsHash        // 直接相信数据库里的摘要字段
const approval = approvals.byToolCall(record.id)
// 绑定比对：approval.paramsHash === paramsHash   → 永远为真
// 实际执行：transport.call(tool.name, call.args)  → 用的是 args
```

绑定比的是 `params_hash` 字段，执行用的是 `args`。两者一旦不同步——有人改了参数却没改摘要——审批绑定就被整个绕过：**审批批的是「查 9 月费用明细」，实际执行的是「查 8 月费用明细」**。

**根因**

不是逻辑写错，是**数据模型设计错了**：把「参数的摘要」当成了一个可以独立存储、独立读写的字段，而不是参数的一个派生值。派生值一旦被物化，就多了一份可能与源数据不一致的副本。

这和「缓存与源数据不一致」是同一类问题，只不过后果是安全边界失效。

**取舍**

有三种修法：

| 方案 | 评价 |
|---|---|
| 加数据库约束/触发器保证一致 | SQLite 里能做到，但把业务不变量推进 DDL，可读性差，且换库就废 |
| 只在写入路径上保证一致 | 防不住绕过写入路径的改动（直接改库、运维脚本、备份恢复） |
| **读取时从参数现算摘要并核对** | 选了这个 |

选第三个的理由：**安全边界不能依赖「没有人会绕过正常写入路径」这个假设**。审批的意义就是在有人试图绕过时能挡住，所以校验必须放在执行前的那一刻，基于当下的数据现算。

**修法**

```ts
// 摘要由参数现算，并与记录里的那一份核对
const paramsHash = hashValue(call.args)
const tampered = paramsHash !== record.paramsHash

if (tampered) {
  // 排在所有权限检查之前——不是「能不能调」，而是「这条记录还作不作数」
  deny(ErrorCode.APPROVAL_PARAMS_DRIFT, `参数与记录中的摘要不一致，记录已被改动`)
}
```

位置也刻意选过：它是**记录自洽性检查**，不是权限规则，所以放在权限链之前——先确认「这条记录还是不是原来那条」，再讨论「能不能执行」。

同时补了两个回归样本钉死它：一个只改参数（细的攻击）、一个连摘要一起改（粗的攻击，会被审批绑定本身挡住）。

**可以怎么讲**

> 审批绑定看起来只是「比对两个哈希」，但我在写攻击用例时发现绑定比对的是数据库里的摘要字段，而执行用的是参数本身——只改后者，绑定看上去仍然匹配。根因是我把派生值物化了，多了一份可能与源数据不一致的副本。修法是读取时从参数现算摘要并核对，并且放在权限链之前，因为它是记录自洽性检查而不是权限规则。这个问题的教训是：安全边界的校验必须基于执行那一刻的数据现算，不能依赖「没有人会绕过正常写入路径」。

### 2. 审批绑定到了占位符版本：一条本该正常的审批莫名失效

**现象**

M2 做完后在 CLI 上走完整发布流程：发起发布 → 批准 → 确认。批准成功，确认时报：

```
[APPROVAL_INVALID] 工具 "mcp__publish__publish_report" 的版本已从 unknown 变为 a5710d33f58898ed，审批需重做
```

问题是这条审批刚刚才批准，工具版本怎么会变。

**根因**

`requestPublish` 创建审批时，工具版本取自 `registry.get(toolName)?.toolVersion ?? 'unknown'`。而工具注册表是在 Source 建立连接时才填充的。

CLI 是独立进程：`publish` 命令只发起发布，从没跑过任务，所以 Source 还没建起来，注册表是空的 → 工具版本绑成了字符串 `'unknown'`。

到 `confirmPublish` 时才 `await prepare()` 建起 Source，这时真实版本是 `a5710d33...`，和 `'unknown'` 对不上 → 判定审批失效。

**为什么 API 路径没暴露这个问题**

HTTP 路径下，同一个进程里任务已经跑过（`POST /sessions/:id/run`），Source 早就建好了，所以绑到的是真实版本。**同一个 bug 只在进程生命周期不同的调用路径上显形**——这是分布式/有状态系统里很容易漏的一类缺陷，单测很难覆盖到，只有端到端换一条入口才看得见。

**取舍**

| 方案 | 评价 |
|---|---|
| 保持同步、把 `'unknown'` 当合法值 | 等于把「绑定到一个未知版本」当成正常情况，安全边界形同虚设 |
| 建 context 时就建好所有 Source | 启动变慢，且配置有问题的数据源会拖住整个进程 |
| **改成异步，先 `prepare()` 再绑定；绑定不到就直接报错** | 选了这个 |

第三个方案有两层：一是把顺序修对（先建连接再绑定），二是**把静默降级改成显式失败**——绑不到工具版本说明系统状态不对，这时报错比绑一个占位值正确得多。占位值的危险在于它不会当场报错，而是在几小时后以「审批莫名失效」的形式爆出来，排查成本极高。

**修法**

```ts
async requestPublish(reportId, request) {
  await this.deps.prepare()               // 先确保工具已注册
  const toolVersion = this.deps.toolVersionOf(toolName)
  if (!toolVersion) {
    // 宁可直接报错，也不要绑一个占位版本
    fail(ErrorCode.TOOL_NOT_REGISTERED, `发布工具 ${toolName} 未注册，无法生成发布确认`)
  }
  ...
}
```

**可以怎么讲**

> 我在 CLI 上走发布流程时，批准之后确认报「工具版本从 unknown 变成了真实版本，审批需重做」。根因是发起发布时 Source 还没建起来，工具版本绑成了占位符 `'unknown'`。API 路径没暴露这个问题，因为同一进程里任务已经跑过、Source 早建好了——同一个 bug 在不同进程生命周期下表现不同。修法是两层的：把顺序改对（先 prepare 再绑定），更重要的是把静默降级改成显式失败。绑一个占位值不会当场报错，而是几小时后以「审批莫名失效」的形式爆出来，排查成本高得多。

### 3. 恢复时走的可能是另一条计划

**现象**

M4 写单元测试时，一个「参数没被改动、应当正常放行」的用例失败了，报 `GUIDE_NOT_READ`——但计划的第一步就是读 guide。

**排查**

打日志看轨迹：会话在恢复后继续往下跑，依次读了 publish 的 guide、然后去调 `erp.list_business_units`，而 erp 的 guide 从没读过。

不对劲的地方在于：这个会话用的内联计划只有两步（读 finance guide → 调费用明细），根本不该出现 publish 和 erp。

**根因**

`runSession(id, { plan })` 允许调用方覆盖计划（回归样本用它构造违规路径），但 `resumeSession(id)` 里写死的是 `loadSkillPlan(skill)` —— **Skill 自带的计划**。

两者不是同一份。恢复时重放完被批准的那一步之后，循环要继续往下走，而「下一步是什么」由规划器决定——于是它沿着 Skill 的 11 步计划跑，和当初 2 步的内联计划完全不是一回事。

**为什么之前没暴露**

之前用内联计划 + 恢复的两个回归样本碰巧躲过了：它们的内联计划是全量计划 + 一个敏感步骤（12 步），而 Skill 自带计划是 11 步。恢复后 `history.length = 12`，规划器去取 `steps[12]` 得到 `undefined` → 直接收尾。**长度凑巧对上了，bug 被掩盖了**。

这次单元测试的计划只有 2 步，凑巧不上了，问题才浮出来。

**取舍**

关键判断：计划到底是什么？

- 它不是 Session 的持久状态（真实 LLM 后端根本没有计划文件）
- 它是**规划器的输入**，由调用方在启动一次执行时提供

所以「恢复要用哪份计划」的答案是：**谁提供的，谁就要再提供一次**。把它持久化到 Session 上，等于让一个纯测试/扩展机制污染生产数据模型。

| 方案 | 评价 |
|---|---|
| 把计划持久化进 Session | 生产路径根本不需要，为了覆盖测试场景引入一个永久字段 |
| 在内存里记住每个 Session 用的计划 | 进程重启就丢了——而重启恰恰是恢复最主要的场景 |
| **把计划作为参数一路传下去** | 选了这个 |

**修法**

`resumeSession` 和 `runRecovery` 都接受可选的 `plan`，与 `runSession` 保持对称；`planFor(sessionId, override)` 统一「覆盖过就用覆盖的，否则用 Skill 自带的」。

同时把这个约束写进文档和代码注释：**覆盖过就必须一路覆盖**。

**可以怎么讲**

> 一个「应当正常放行」的单元测试报了 guide 未读，但计划第一步就是读 guide。打轨迹发现恢复后系统在跑另一个计划——`runSession` 允许覆盖计划，但 `resumeSession` 里写死了 Skill 自带的计划，恢复时重放完那一步之后沿着错误的计划继续。之前两个回归样本碰巧躲过了：它们的计划长度和 Skill 计划正好差一步，取到 `undefined` 就收尾了。判断的关键是「计划是什么」：它不是会话的持久状态，而是规划器的输入。所以答案是「谁提供的谁再提供一次」，而不是把它持久化——那等于为了测试场景污染生产数据模型。

### 4. 读 guide 成了绕过 Workspace 边界的小路

**现象**

M2 加完权限链后跑回归，跨 Workspace 的样本失败：期望 `WORKSPACE_BOUNDARY_VIOLATION`，实际报 `SOURCE_NOT_ACTIVE`，而且中断在 `read_source_guide` 上。

**根因**

权限链的 Workspace 边界检查只作用于「Source 工具」（`tool.kind === 'source'`）。内置的读 guide 工具不属于任何 Source，所以整条边界检查被跳过，只在后面一个临时加的「目标 Source 是否激活」判断里被拦下——于是错误码指错了原因。

这不是个「错误码不好看」的小问题：

1. **`SOURCE_NOT_ACTIVE` 会把排障引向错误方向**——看到它的人会去查 Skill 配置，而真正的问题是没有权限。
2. **更要紧的是它确实是一条越权路径**。guide 里写着该数据源的参数范围、结果契约、敏感数据约定。跨 Workspace 读到别人的 guide，本身就是信息泄漏——不是「无害的元数据」。

**取舍**

| 方案 | 评价 |
|---|---|
| 在 `executeGuideRead` 里加特判 | 修了症状：错误码还是不对，且「哪些检查适用于内置工具」散在两处 |
| 给内置工具加 `kind: 'source'` 伪装 | 语义错误，且会让它被当成 Source 工具做 Schema 校验 |
| **引入「调用主体（subject）」概念** | 选了这个 |

**修法**

`subjectSourceOf(tool, args)`：Source 工具的主体是它自己；读 guide 工具的主体是**参数里指定的目标 Source**；其它内置工具没有主体。

权限链的边界与激活检查统一改为检查 `subjectSourceSlug`，而不是 `tool.sourceSlug`。这样：

- 读 guide 与调工具受**同一套**边界约束
- 读 guide 本身不需要先读过 guide（检查 4 只在 `tool.kind === 'source'` 时生效）
- 错误码指向真实原因

**可以怎么讲**

> 权限链的 Workspace 边界只作用于 Source 工具，而内置的读 guide 工具不属于任何 Source，于是整条边界检查被跳过——读别人的 guide 变成了一条越权路径。这不是错误码不好看的问题：guide 里写着参数范围和结果契约，跨 Workspace 读到它本身就是信息泄漏。修法是引入「调用主体」概念——Source 工具的主体是它自己，读 guide 工具的主体是它指定的目标 Source，权限链统一检查主体。这样读 guide 和调工具受同一套边界约束，而读 guide 又不要求先读过 guide。

### 5. 让「结果未知」保持未知，而不是假装它是失败

**现象**

设计 M3 的崩溃恢复时遇到一个无法回避的问题：`tool_call` 停在 `pending` 状态，进程挂了。

**这时的系统状态是**：我们**无法确定** Source 那边到底执行了没有。请求可能发出去了、可能没有；可能执行成功但结果没写回来。

**取舍**

三条路：

| 方案 | 评价 |
|---|---|
| 当作「没执行」，重启后重放 | 对只读源安全（数据确定性），但对有副作用的操作可能是重复执行 |
| 当作「执行了」，标记成功 | 更危险：可能根本没执行，后续步骤基于一个不存在的输入往下走 |
| **标记为 `EXECUTION_INTERRUPTED`，转 PAUSED，等显式恢复** | 选了这个 |

选第三个的理由：**前两个方案都在「编造一个我们不知道的事实」**。系统的诚实性比流畅性重要——一个明确说「我不知道」的系统，和一个悄悄猜一个答案的系统，在审计场景下的价值完全不同。

具体落地时又分了两层：

1. **只读调用重放是安全的**——数据源是确定性的，重新取一次得到同样的结果。所以恢复可以让它重放。
2. **但「结果未知」这件事本身必须记下来**——所以先标记成 `EXECUTION_INTERRUPTED` 再转 PAUSED，而不是静默重放。

同时把恢复拆成 `scan()`（只读，报告会怎么处置）和 `recover()`（才动状态）。服务启动时只**报告**，不自动执行任何带副作用的动作——一启动就重放一堆调用，比停下来等一句指令危险得多。

**这个设计后来救了一次**

M4 的发布场景里出现了一个真正的窄窗口：网关已经投递成功，进程在写回 `report.receiptId` 之前挂掉。重启后看到的是「报表还是 draft」，但东西已经发出去了——**此时重放就会发两次**。

这里「让未知保持未知」的思路直接给出了解法：`reconcilePublish` 去查网关回执，三种判定对应三种正确动作（补记 / 可重试 / 转人工），而且**这个方法从不调用发布工具**——它存在的意义就是不重发。

**可以怎么讲**

> 崩溃恢复里最难的不是写恢复逻辑，而是承认有些事我们不知道。`tool_call` 停在 pending 时，我们无法确定 Source 那边执行了没有。当时有三条路：当作没执行去重放、当作执行了标记成功、或者标记为「中断，结果未知」转人工态。前两个都在编造一个我们不知道的事实——一个明确说「我不知道」的系统，和一个悄悄猜一个答案的系统，在审计场景下的价值完全不同。这个思路后来直接解决了发布场景的一个真窄窗口：网关已经投递、本地还没记账，此时重放就会发两次。解法是查网关回执，而且这个方法从不调用发布工具——它存在的意义就是不重发。

### 6. 框架在钩子之前就把参数拦掉了：整条权限链被绕过

**现象**

把循环换成 `pi-agent-core` 的 `Agent` 之后，`schema-invalid-rejected` 样本在 pi 下没通过。期望是「被拒 → `BLOCKED`」，实际轨迹里那条非法调用**一条记录都没有**：没有 `tool.call.requested`，没有 `permission.decided`，Session 最后的去处也不对。

**根因**

整个 PreToolUse 设计的隐含前提是：**每一次工具调用都会先经过我们的钩子**。

这条前提在 legacy 循环里成立，因为循环是我们自己写的、调用是我们自己发起的。pi 的顺序不是这样——它在调 `beforeToolCall` **之前**就按工具声明的 JSON Schema 校验参数。非法参数根本进不了钩子，直接变成一条 error toolResult。

于是出现一个很难受的状态：那个「唯一的闸口」被绕过去了，而且是**静默地**。审计上看起来像「模型想调一个非法工具，系统什么都没做」；实际上拒绝确实发生了，只是不是我们拒的，所以没有任何我们生成的事件。

**取舍**

| 方案 | 评价 |
|---|---|
| 放宽工具 schema，全部交给我们的钩子校验 | 放弃框架自带的一层检查；而且 pi 仍要用 schema 生成工具声明，两边会分叉 |
| 在 `execute` 里兜底 | 非法参数到不了 `execute`，兜不住 |
| **识别「开始执行却没经过钩子」的调用，补记一条被拒记录并中止** | 选了这个 |

**修法**

订阅 pi 的事件流，让两个事件互相印证：

- `tool_execution_start` —— 记下这次调用的工具名与**真实参数**（此时钩子确实没跑）
- `turn_end` —— 看这一轮的工具结果里，有没有一条「不在我们 pending 表里、且 `isError`」的结果

命中即判定为「被 pi 前置校验拦下的调用」。补一条 `tool_call` 记录（参数取事件流里的真实值，不编造）、补 `permission.decided(deny, SCHEMA_INVALID)` 与 `tool.call.failed`，然后 `abort()`，把 Session 落到 `BLOCKED`——**和 legacy 的语义完全一致**。

`paramsHash` 同样由事件流里的参数现算，不从错误信息里猜。

值得一提的是：抓住这个问题的是**迁移之前就写好的回归样本**。先测边界、再换执行引擎，这个顺序让「框架改变了你的假设」这件事当场暴露，而不是等到线上。

**可以怎么讲**

> 把循环换成框架之后，我发现有一条防线被静默绕过了：框架在调用我的钩子**之前**就做了参数校验，非法参数到不了钩子，于是「每一次调用都会被记录和判定」这个前提失效了。这暴露的是一个更普遍的问题——把控制权交给别人的循环时，必须重新验证「我的断言点是不是仍然是唯一入口」，而不是假设它还是。修法是订阅框架的事件流，用「执行开始」和「轮次结束」两个事件交叉识别出没经过钩子的错误结果，补记录、补判定、再中止。抓住它的是迁移之前就写好的回归样本：先测边界再换引擎，这个顺序让我当场发现假设变了。

### 7. 「hook 内 await」的代价：一个已经被修过的漏洞，换了循环又长出来

**现象**

审批最终选了「hook 内 await」：`beforeToolCall` 里直接 `await approvalGate.waitFor(id)`，批准后从同一位置继续，不重放调用。

这个选择带来一个结论，我一度写进了 README：**参数一直在内存里，所以「恢复时读到被改过的参数」这条路径在 pi 下不存在**。据此把 `approval-params-drift-rejected` 标成了 legacy-only。

写这份复盘、回头核对恢复代码时发现：这个结论**只对了一半**。

**根因**

hook 内 await 只覆盖「进程还活着」的情况。进程被杀之后，恢复仍然要从 `tool_call` 表里把参数读回来——**这正是一条会重读磁盘数据的路径**。

而 pi 的 `resume()` 当时直接拿 `call.args` 去执行，没有像 legacy 那样重算摘要。也就是说：问题 1 里修过的那个洞，换了执行引擎之后**又长出来了**，而且被一句「不存在这条路径」的结论盖住了。

**取舍**

| 方案 | 评价 |
|---|---|
| 维持 legacy-only 的结论，认为 pi 下没有这条攻击面 | 结论是错的，跨进程恢复就是这条攻击面 |
| 把参数连同摘要存进审批记录，恢复时用审批里的参数 | 等于把审批记录做成第二份参数来源，仍然是物化 |
| **恢复时由 `call.args` 现算摘要，与记录里的 `params_hash` 比对** | 选了这个，与 legacy 完全一致 |

**修法**

`PiAgentRunner.resume()` 拿到悬挂调用之后、查审批之前，先做记录自洽性检查：

```ts
const actualParamsHash = hashValue(call.args)
if (actualParamsHash !== call.paramsHash) {
  // 记录已被改动 → APPROVAL_PARAMS_DRIFT → BLOCKED
}
```

位置仍然在权限检查之前——它不是权限规则，是「这条记录还作不作数」。

同时补了一个 pi 专用样本 `approval-params-drift-rejected-after-restart`，流程是 `run → restart → tamper-params → decide → resume`。legacy 那个样本没有 `restart`，因为 legacy 的 `run` 会返回、恢复本来就重读数据库；pi 的 `run` 不返回，必须先把进程杀掉，「重读」才谈得上发生。

**可以怎么讲**

> 审批我选了「在钩子里原地 await」，好处是不用持久化「停在哪」。但我一度把这个好处推导成了一个错误的结论：参数一直在内存里，所以恢复时被篡改的问题不存在。核对代码时发现它只覆盖进程活着的情况——进程被杀之后恢复仍然从库里重读参数，而新循环里我漏掉了 legacy 已经做过的摘要重算。同一个漏洞换了执行引擎就又长出来了。教训是：安全性质要挂在「数据从哪来」上，不能挂在「这条流程通常怎么走」上；而且每条恢复路径都得单独测，不能因为一条路径验过就推广到另一条。

### 8. 为什么最后没接 pi-durable：库要接管的那一层，正好是你要控制的那一层

**背景**

第三步的原计划是直接接 `@earendil-works/pi-durable` 的 `Harness` + JSONL 存储来做检查点恢复。看完它的模型之后，我没有接。

**根因**

pi-durable 的 `Harness` **自己拥有循环和任务调度**，它管理 `ConversationDoc`、`ToolTask`、`replay` 语义。接进来意味着：

- 第 2 步刚换上的 `Agent` 又要被换掉一次；
- Session / 审批 / 检查点要迁进它的 document 体系；
- 而它要接管的，恰好是我们最需要自己控制的那一层。

而这里的真实需求只有一条：**进程在审批等待中被杀掉后，能接着跑完，且不重新规划。**

**取舍**

| 方案 | 评价 |
|---|---|
| 接 pi-durable Harness | 白拿 task 编排、compaction、多会话调度；代价是第二次大重构，且把权限边界挪进第三方抽象 |
| **只借它的 JSONL 存储思路，自己实现恢复** | 选了这个 |
| 不做持久化，重启后从头跑 | 已完成步骤会重放、审批要重做一遍——等于承认「长任务」不成立 |

**修法**

`TranscriptStore`：`data/agents/<sessionId>.jsonl` 追加写，容忍最后一行被截断（进程被杀时正在写）。

恢复 = 读对话记录 + 读 `tool_call` 表里的悬挂调用 → 执行被批准的调用 → 补一条 `toolResult` 消息 → `new Agent({ initialState: { messages: [...transcript, toolResultMessage] } })` → `agent.continue()`。

**不重新规划**：模型看到的是原来那份上下文，而不是重跑一遍 Skill 计划。

这条路径用真正的跨进程验证过：进程 A 停在审批处直接 `process.exit(0)`，进程 B 恢复后到 `READY`、7 次取数、无重复调用。

**可以怎么讲**

> 这一步我本来打算直接接 pi-durable 的 Harness，看完它的模型后没接。原因是它自己拥有循环和任务调度，接进来等于把上一步刚换上的 Agent 再换一次，还要把 session、审批、检查点全迁进它的文档体系——而权限边界恰恰是我最不该交出去的那一层。我的需求其实只有一条：进程被杀之后能接着跑完、不重新规划。所以我只借了它 JSONL 存储的思路，自己实现了对话记录和恢复。判断依据是「这个库要接管的那一层，是不是正好你要控制的那一层」——如果是，就不该接，哪怕它能省一部分代码。

### 9. 保险机制被自己提前撤掉：一封邮件差点发两次

**现象**

自审发布网关时发现：真实邮件投递前会写一条「意图」记录，投递成功后删除。但删除发生在写回执**之前**：

```ts
await sendMail(...)       // 信已经发出去了
rmSync(intentPath)        // ← 意图在这里就删了
copyFileSync(...)         // 归档副本
appendFileSync(receipts)  // 回执最后才写
```

如果进程在这中间死掉，磁盘上既没有回执、也没有意图。恢复扫描据此判定「从没发过」，下一次投递就会再发一封——而邮件是收不回来的。

**根因**

「结果未知」这条边界是由**两个文件的相对顺序**保证的：意图在发送前出现、在回执落盘后消失。我把撤除条件写成了「发送成功」，而真正的安全条件是「**记账完成**」。

每一步单独看都合理（发送成功 → 清理意图），组合起来却打开了一个窗口。凡是「先做 A 再做 B」的清理逻辑，都要问一句：**B 失败时 A 还在不在。**

**取舍**

| 顺序 | 结果 |
|---|---|
| 发信 → 删意图 → 写回执 | 有重发窗口（当时的实现） |
| **发信 → 写回执 → 删意图** | 无窗口：中间失败则意图还在，下次被拦 |
| 永不删意图，只靠回执优先 | 也能对，但意图目录会无限增长 |

选了第二种。

**修法**

把 `rmSync(intentPath)` 挪到回执 append 之后。改完的语义：

- 发送明确失败（连不上、被拒）→ 删意图，允许重试
- 发送成功但后续任何一步失败 → 意图留下 → 下次调用以 `RECEIPT_UNKNOWN` 停下，转人工
- 全部完成 → 回执落盘后才删意图

补了一条专门钉这个顺序的测试：把投递目标路径先占成一个目录，让 `copyFileSync` 必然失败，然后断言「信已发出（.eml 落盘）、回执为空、意图还在、再投一次被拒绝、收件箱仍然只有一封」。

**可以怎么讲**

> 我在做「结果未知不能重发」的保险时，给每次投递写了一条意图记录：成功后删除、失败后保留。后来自审发现，我把删除放在了写回执之前——信发出去了、意图删了、回执没写，进程这时挂掉，磁盘上两条记录都没有，恢复逻辑就会认为从没发过，然后重发一封邮件。根因是我把撤除条件写成了「发送成功」，而真正的安全条件是「记账完成」。修法是把删除挪到回执落盘之后，并加了一条测试：故意让写回执失败，断言意图还在、下一次投递被拦。这件事让我形成一个检查习惯：凡是「先做 A 再做 B」的清理逻辑，都要问一句 B 失败时 A 还在不在。

### 关于第 15 条：一句话发起，不能只是把话存下来

**现象**

接口和 CLI 都有 `request` 字段，任务里也完整记录了需求原文。但真正决定跑几月份的是 `input.period`：

```bash
npm run cli -- run -w group-finance -p 2025-06 -r "出 2025 年 8 月的月报"
#                                                  ↑ 跑的是 6 月，不报错
```

**根因**

把「记录需求」当成了「理解需求」。`request` 进了事件轨迹、能审计，但没参与执行决策——所以它更像一个备注字段，而不是输入。

这和审批漂移是同一类问题：**说的是 A，做的是 B，而且两边都不会报错**。

**取舍**

| 方案 | 评价 |
|---|---|
| 直接把 `request` 丢给 LLM 解析 | 需要外部依赖与 key；而且这一步要的是确定性，不是灵活性 |
| 不解析，强制要求调用方给结构化输入 | 等于承认「自然语言发起」是假的 |
| **加一层确定性的文本解析** | 选了这个 |

选第三个的理由：**期间的识别是确定性问题，不需要语义理解**。`2025 年 9 月`、`2025-09`、`上个月` 这些表达用正则加一点点规则就能覆盖，而且可测、可复现、无外部依赖。真正需要语义理解的是「重点看华东」这类诉求——那才该交给 LLM。

**修法**

`resolvePeriod()` 三条规则：

1. 显式输入优先，但若需求里写的是另一个期间 → `REQUEST_PERIOD_CONFLICT`，**不替调用方选一个**。
2. 没有显式输入 → 从需求文本里解析。
3. 都没有 → `REQUEST_PERIOD_MISSING`；出现多个矛盾期间 → `REQUEST_PERIOD_AMBIGUOUS`。

识别结果与来源（`explicit` / `parsed`）写进 `session.created` 事件，事后能追溯「这次跑的到底是哪个月、依据是什么」。

解析本身也有个细节值得记：「上上个月」里包含「上个月」三个字，分开匹配会同时算出两个期间，把一个本来明确的句子判成「歧义」。用一个按长度排序的交替正则可以保证只命中更长的那一个——这类「短模式是长模式的子串」的问题在中文里很常见。

**同时补的入口**

CLI 的 `-p` 不再是必填；WebUI 的任务页加了发起框，用户只写一句话就能发起并执行。

**可以怎么讲**

> 这块我一开始做成了「需求被完整记录但没参与执行」——接口有 request 字段、事件轨迹里也有，但真正决定跑几月份的是结构化输入，两者不一致时系统不报错。这和审批漂移是同一类问题：说的是 A、做的是 B、而且看起来一切正常。修法是加一层确定性的需求解析：能从文本识别期间，识别不到就报错，两者矛盾就报冲突。判断的关键是「这一步需不需要语义理解」——识别会计期间是确定性问题，正则加规则就能覆盖、可测可复现；真正需要理解的是「重点看华东」这类诉求，那才该交给 LLM。

### 关于第 16 条：模型配置要显式，不能靠约定

**现象**

`createAppContext` 里硬编码了 `new MockAgentBackend(...)`。想接真实模型，得改代码。

**根因**

M1 阶段「默认 Mock」只是写死在代码里的一个事实，不是一个可配置的决策。当成本/能力/合规需要按环境切换时，这个事实就必须变成配置。

**取舍**

| 方案 | 评价 |
|---|---|
| 每处调用各自读环境变量 | 配置散落，且无法在启动时统一校验 |
| 把 key 写进 `datasentry.config.json` | 密钥进版本库，最糟的一种 |
| **配置文件只写「去哪个变量取」，值留在环境；启动时校验** | 选了这个 |

四条具体决定：

1. **密钥不落配置文件。** 配置里写 `apiKeyEnv: "DATASENTRY_MODEL_API_KEY"`，值从环境读。这条和 Source 凭据是同一套规矩——凭据只在注入点出现。
2. **启动时校验，不是首次调用时。** provider 拼错、选了 `anthropic` 却没有密钥，都在 `createAppContext()` 就失败。理由和第 2 个问题（占位符版本）一样：**错误的暴露位置要尽量靠前**。
3. **能力差异按型号判定。** `thinking: {type:"adaptive"}` 和 `output_config.effort` 在老模型上会直接 400。所以按型号前缀判断该不该发这些参数——**宁可少发一个参数，也不要发一个会报错的参数**。
4. **回归样本永远用 Mock。** 只要显式传了 `plan`，后端就选确定性规划器。这样 `datasentry.config.json` 怎么改都不会影响回归结果的可复现性——**验证边界的那套测试不能被被验证对象的配置影响**。

顺带补了一个 M5 的健壮性修复：模型调用抛异常原本会裸奔出 `run()`，把 Session 永远留在 `FETCHING`。现在在 `fetchLoop` 里接住，转成 `MODEL_CALL_FAILED` 并正常落到 `FAILED`——**任何一步「没走成」都必须有一个终态，不能让任务卡在中间**。

**可以怎么讲**

> 模型一开始是写死的 Mock，后来要支持切换真实模型。核心判断是三条：密钥只写环境变量的**名字**不写值，和凭据管理同一套规矩；配置错误在启动时就报，不等到第一次调用；模型能力按型号判定，老模型不支持 adaptive thinking，发过去会 400，所以宁可少发一个参数也不要发一个会报错的。另外回归样本强制走 Mock——验证边界的那套测试不能被被验证对象的配置影响。

### 关于第 17 条：同一条规则，用错了对象

**现象**

接上真实模型后跑 API 冒烟，发布那一步报：

```
GUIDE_NOT_READ — 调用 "publish" 的工具前必须先读它的 guide
```

Mock 规划器每次都读齐 5 个 guide，所以从没触发过。真实模型读完 4 个就判断「够用了」，跳过了 publish——于是发布被拦。

**根因**

`requiresGuide` 这条规则的意图是：**Agent 不该调用自己没读过契约的工具**。它防的是「模型凭想象传参数」。

但 `publish_report` 不是 Agent 调的。它由人工流程触发（发起确认 → 审批 → 确认投递），Agent 只负责产出草稿。

规则本身是对的，**套用对象错了**。

**取舍**

| 方案 | 评价 |
|---|---|
| 让 Agent 必须读 publish guide | 把人工流程的正确性押在模型是否听话上 |
| 在发布流程里替 Agent 标记 guide 已读 | 伪造状态，审计轨迹会失真 |
| **把该工具的 `requiresGuide` 设为 `false`，并在 guide 里写清「这个 Source 由人工调用」** | 选了这个 |

理解检查并没有被取消——它由**审批**承担：审批界面展示文件、格式、接收人与内容摘要，那才是这个动作真正需要被理解的地方。

**可以怎么讲**

> 接真模型后发布被 guide 门禁挡住了，因为模型跳过了读 publish 的 guide。查下来发现规则用错了对象：`requiresGuide` 防的是「Agent 调它不理解的工具」，而发布是人工流程触发的，Agent 根本不该调它。修法不是让模型必须读，而是把这个工具的 guide 门禁关掉，并在 guide 里写清它由人工调用——理解检查交给审批，审批界面会展示文件、格式、接收人和摘要。同一条规则套错对象，会让正确的流程看起来像故障。

## 三、贯穿全程的判断原则

把上面这些提炼一下，会发现反复出现同一批判断题。这部分是「你的工程判断是什么」的答案。

### 1. 边界检查的顺序，就是错误码的语义

权限链七道检查的顺序不是随便排的：

```
工具已注册 → Workspace 边界 → Source 已激活 → guide 已读 → 参数 Schema → 审批有效性 → 敏感级别
```

- **边界排在「已激活」之前**：跨 Workspace 的 Source 同时也一定没激活。若顺序反过来，越权会被报成 `SOURCE_NOT_ACTIVE`——错误码指错了原因，排障的人会去查 Skill 配置。
- **审批有效性排在「敏感级别」之前**：它们回答同一个问题的两面——「这个动作需不需要审批」和「该动作身上的审批还算数吗」。审批无效就明确报失效原因；退回「需要审批」会让一条已经批准的调用看起来像从没批过。
- **记录自洽性排在所有权限检查之前**：不是「能不能调」，而是「这条记录还作不作数」。

**一条拒绝如果没有指向真实原因，它就只是噪音。**

### 2. 派生值不要物化

摘要字段与参数不同步导致绑定被绕过（问题 1）、时间戳排序不稳定（速查 9）、guide 状态两处存储会不一致（速查 10）——都是同一个模式：**能算出来的东西不要存**。

存下来就多一份可能与源数据不一致的副本，而且不一致的时候通常不会当场报错。

这条原则不是「记住一次」就够的：问题 7 里，同样的摘要校验在换掉执行引擎之后又被漏掉了。**原则要落到每一条新路径上，而不是只落在你第一次想到它的那条路径上。**

它还有一个同族形态：**同一份事实不要写两遍**。事件既写库又写 JSONL 时，一旦没指定谁是事实源，写文件失败就会把一次已经落库的操作变成假的失败。做法是把库定为唯一事实源，JSONL 降级成可重建的导出。

### 3. 静默降级比直接失败危险

绑一个占位符版本（问题 2）、拿空字符串当凭据继续跑、把未知结果猜成失败——这类「先让它跑起来」的处理，危险在于**不会当场报错**，而是在几小时或几天后以一个难以定位的形式爆出来。

反过来说，一个显式的失败至少有两个好处：位置明确，以及它不会伪装成成功。

### 4. 让「未知」保持未知

接上一条的另一面。系统里有三类状态，不能压缩成两类：

- 成功
- 失败
- **不知道**

把第三类归进前两类，就是在编造事实。发布场景里这条直接决定了「会不会重复发一遍给董事会」。

### 5. 测试失败时，先问哪一边错了

速查 12 里，样本红了，但**系统是对的**——拿部分口径去比对全量口径，本来就该判冲突。

「测试失败 → 改代码让它变绿」是最常见的错误反射。正确的第一步是判断：是实现的期望不对，还是我对系统的期望不对。

### 6. 覆盖率是手段，路径覆盖才是目的

PRD 要求「样本覆盖 8-10 类路径」。做法不是凑够 10 个 `it`，而是：

- 给每个样本一个 `path` 字段，明确它对应哪一类
- 回归报告按 `path` 统计 `通过数/总数`
- 报告顶部直接打出 `覆盖路径 10 类：拒绝(3/3) 审批(2/2) ...`

**没有分母的覆盖率是自我安慰。**10 类里有 1 类没样本，报告上写的是 `部分结果(0/0)`——一眼能看出来，而不是隐没在「100% 通过」里。

### 7. 回归能力要能被推翻自己

`restart` 是一个 flow 动作：它会关掉当前的 `AppContext`，在**同一份数据目录**上重新起一个。内存缓存、MCP 子进程、guide 已读状态全部丢失，只剩 SQLite 与磁盘文件。

这样写而不是「mock 掉持久层」，是因为**恢复逻辑的正确性只取决于真正的重启**。用 mock 验证「重启恢复」，验证的是 mock 的行为。

同理，`tamper-params` 这个动作直接改数据库绕过所有写入路径——因为它模拟的是攻击者，而攻击者不会走你的正常接口。

### 8. 两条路径的结局必须由同一份代码决定

「审批人当场拒绝」和「重启后补记拒绝」是同一件事的两个入口（速查 11）；「确认发布」和「核对回执补记」也是（M4 的 `finalizePublish`）。

**同一件事有两个入口时，如果各写一份实现，迟早会分叉——而分叉的表现形式通常是「重启一次就换了个结局」，这是最难排查的一类 bug。**

### 9. 该失败的地方要失败得早

- Source 配置在**加载时**校验（而不是调用时）
- local handler 在**建连接时**核对齐全（速查 3）
- 凭据在**注入前**要求存在，缺失就报错（而不是拿空字符串）
- 参数 Schema 在**执行前**拦下（而不是等 Source 返回错误）

这类校验的共同价值：把错误的暴露位置从「半小时后的某个难懂的报错」提前到「配置文件改错的那一秒」。

### 10. 把循环交给框架时，先确认它没有在你的断言点外面动手

自己的循环里，有一批断言看起来是「显然成立」的：

- 每次工具调用都会从我的钩子过一遍
- 每个工具结果都会被我校验
- 每次状态变更只有一个地方决定

它们之所以显然，是因为它们由**你的代码结构**保证。换成别人的循环之后，同样的句子就变成了关于**别人控制流**的假设——而假设是会失效的，失效的时候还不会报错（问题 6）。

所以迁移时第一件事不是「把钩子挂上去」，而是问：**这个框架在我的钩子之前和之后，还会做什么？** 答案要靠读源码和执行事件流，不能靠文档里的「调用前会触发 hook」。

最便宜的验证方式是跑原有的负向样本。它们本来就写着「哪些事必须被拒绝」——如果换了引擎之后仍然一条条被拒绝，说明断言点还在；如果有哪条静默地不再发生，那就是防线被绕过了。

**能从别人的框架里拿走的，是循环；不能拿走的，是可被断言的控制点。**

## 四、如果被追问

**Q：这个项目最难的地方是什么？**

A：不是写 Agent 循环，而是让「Agent 的动作」和「人对 Agent 的授权」始终对得上。审批绑定、参数摘要、草稿版本、接收人摘要、去重键——这些都是同一件事的不同侧面：**证明现在要执行的动作，正是当初被批准的那个**。而这件事的难点在于，它有无数个可以悄悄不一致的地方（占位符版本、摘要字段与参数不同步、恢复时换了计划）。

**Q：你用了 pi，和「不用现成框架」矛盾吗？**

A：我把这件事分成两层：**循环是商品，边界是业务**。pi 的 `Agent` 提供循环和多 provider 层，这部分没有差异化价值，自己写只是重复劳动；但权限链、审批绑定、状态机、恢复仍然是我们自己的，只挂在它的 `beforeToolCall` 和事件流上。迁移时我验证了一件事：它的控制流有没有在我的断言点外面动手。结果是有一条——Schema 校验跑在钩子之前，非法参数根本进不了钩子（问题 6）。补了识别逻辑之后，两边的语义才真正一致。所以问题不是「用不用框架」，而是「框架和你的控制点谁在外面」。

**Q：为什么不直接用 pi-durable 做检查点恢复？**

A：因为它要接管的那一层，正好是我要控制的那一层（问题 8）。它自己拥有循环和任务调度，接进来等于把刚换上的 `Agent` 再换一次，还要把 Session、审批、检查点迁进它的文档体系。而我的需求只有一条：进程被杀之后能接着跑完、不重新规划——用一份 JSONL 对话记录加一次重放就够了。判断标准是「这个库要接管的那一层，是不是正好你要控制的那一层」。如果是，就不该接，哪怕它能省一部分代码。

**Q：为什么 Mock 模型而不是直接接真模型？**

A：因为要先把**边界**测准。Harness 的正确性和模型能力无关——权限链、Schema 校验、状态机、审批绑定、事件轨迹，这些在确定性规划器下能被逐条断言，换成 LLM 之后这些断言一条都不用改。反过来，如果一开始就接 LLM，「回归失败」就分不清是边界错了还是模型随机了。

**Q：这套系统的可扩展性怎么样？**

A：三个扩展点都是加配置不改代码的：接新数据源是加目录（`config.json` + `guide.md`）；新报表类型是加 Skill（`SKILL.md` + `plan.yaml`）；换模型是实现 `AgentBackend` 接口。加权限检查是往 `PRE_TOOL_USE_CHECKS` 数组里插一项。这些都是实际验证过的——M2 加审批检查就是这么加的，没有改调用方。

**Q：有什么已知的不足？**

A：几个明确的：

- 恢复扫描是全量的，任务量上千会变慢，需要按 `updated_at` 加窗口或做增量索引
- 一个 Session 同时只允许一个悬挂的待审批调用（恢复要能唯一确定重放哪一条）；要支持并发审批得先设计「下一步是哪条」的规则
- **默认循环仍是 legacy**。pi 循环已经通过全部回归样本（17/17），但切成默认之前还需要在真实负载下观察——两套循环并存是迁移期的成本，不是长期状态
- WebUI 的 `dist/` 没接入后端静态托管，部署方式留给了实际环境
- `runSession` / `resumeSession` 的计划覆盖必须一路传递，这是覆盖机制的固有约束，不是 bug 但容易踩
